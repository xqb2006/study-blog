今天正式接触到软件工程这门专业课时，对于之前全部依赖ai写代码的我进行了启发。

初步接触各种ai大模型，因为基础薄弱，问题全部依赖ai去完成。但是深入使用发现，总会遇到一些问题，如：

1.一直增加新的功能，ai自己测试自己迭代导致代码出现越来越多的bug，功能不能达到预期要求

2.做出的项目逻辑混乱，可能存在执行效率低下的情况，反复要求ai提升效率收获甚微

3.出错后让ai检查修复时，当逻辑复杂时自然语言可能无法清晰表达出所在问题

4.如果工程量大，需要短时间内开发出成品，团队其他成员较难并行开发

5.新的ai跟进项目开发较为费时费token

今天学习软件工程第一章内容，对于软件生存期模型这个概念有了新的认识和运用的想法

软件生存期模型完整对照总表

| 发展时期            | 模型名称              | 提出年份      | 核心特点                                             | 适用场景                                 |
| --------------- | ----------------- | --------- | ------------------------------------------------ | ------------------------------------ |
| **概念萌芽期**       | 分段模型              | 1956      | 最早的有记录过程模型，划分明确阶段，阶段间有固定输出                       | 早期大型军用系统，结构相对简单                      |
|                 | 迭代模型（雏形）          | 1950年代末   | 允许反复修改和完善，最早实践于SAGE防空项目                          | 技术风险高、需逐步验证的复杂国防系统                   |
|                 | SDLC概念确立          | 1960年代    | “系统开发生命周期”术语正式出现，为后续模型奠基                         | 大型计算机系统开发的宏观管理                       |
| **经典模型时代**      | 瀑布模型              | 1970      | 严格线性顺序，阶段间强依赖；强调前期文档，变更困难                        | 需求明确稳定、技术成熟的项目（如政府报表、小型管理系统）         |
|                 | 增量模型              | 1971      | 分批次交付独立功能模块（增量），用户可较早看到成果                        | 大型项目需快速交付核心功能，需求逐步明确（如电商分期上线）        |
|                 | 演化模型              | 1976      | 从粗糙版本开始，通过用户反馈不断改进，迭代开发早期风范                      | 需求模糊、需探索性开发（如科研软件、原型系统）              |
|                 | V模型               | 1978      | 瀑布变体，呈V字形，左侧开发右侧测试一一对应，强调验证与确认                   | 质量要求极高、需求稳定（如航空航天、医疗设备、安全关键系统）       |
|                 | 螺旋模型              | 1988      | **风险驱动**，四象限迭代（目标→风险→开发→评估），结合瀑布与原型优点            | 大型、复杂、高风险项目（如NASA航天系统、军事指挥系统）        |
| **面向对象与快速开发时代** | 喷泉模型              | 1990      | 面向对象专用，各阶段（分析/设计/编码）重叠且迭代，“无间隙”开发                | 采用面向对象技术（如C++/Java）的项目（如企业级图形界面系统）   |
|                 | 基于构件的开发模型         | ~1990     | 复用预制标准化构件进行组装，强调构件库管理                            | 需快速搭建、大量复用已有模块（如ERP系统、中间件平台）         |
|                 | RAD模型（快速应用开发）     | 1991      | 极短周期（60-90天），大量使用可视化工具和可复用组件，用户深度参与              | 时间紧迫、需求较明确且可模块化的业务系统                 |
|                 | W模型               | 1993      | V模型的发展，强调**测试贯穿整个生命周期**，开发与测试并行                  | 对质量要求高，希望尽早发现缺陷的规范化企业级项目             |
| **敏捷与DevOps时代** | Scrum             | 1995      | 固定周期冲刺（Sprint），三大角色（PO/SM/团队），每日站会与评审            | 需求变化频繁的互联网产品、移动APP开发                 |
|                 | 极限编程（XP）          | 1996      | 强调工程实践（TDD、结对编程、持续集成），简单设计，小版本发布                 | 需求极不稳定、风险高的小型团队（如初创项目、创新产品）          |
|                 | RUP（Rational统一过程） | 1998      | 用例驱动、架构为中心，分四阶段（初始→细化→构建→移交），比敏捷更正式              | 大型企业级项目，需规范又保留灵活性（如银行核心系统、大型政务平台）    |
|                 | 敏捷宣言（统称）          | 2001      | 个体互动 > 流程工具，可工作软件 > 详尽文档，客户协作 > 合同谈判，响应变化 > 遵循计划 | 所有需求易变、交付速度要求高的场景（是Scrum/XP等框架的指导思想） |
|                 | 看板方法              | 2004-2007 | 可视化工作流（看板墙），限制在制品数量（WIP），持续交付，不强制迭代              | 运维支持、维护类项目，需求随时插入、优先级动态变化的场景         |
|                 | DevOps            | 2009      | 开发运维一体化，强调自动化CI/CD流水线，持续监控与反馈                    | 云原生应用、微服务架构，需高频部署（每日甚至多次）的生产环境       |

对于学校的各种软件设计类比赛，我们常常面临着开发时间短（往往从报名到交稿在1个月左右），需要因寻找创新点而不断改动
